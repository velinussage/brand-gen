# Source knowledge and Obsidian vaults

Brand-gen can use local brand knowledge without hard-coding any private paths
into the repo. The context snapshot reports only path metadata and file counts;
agents decide which markdown files to read during a local run.

## Config surfaces

Use `.brand-gen-local.json` for machine-local paths:

```json
{
  "repo_root": "/path/to/brand-gen",
  "vault_paths": [],
  "brand_vault_paths": {
    "sage": ["/path/to/sage/obsidian-vault"]
  },
  "brand_knowledge_base_paths": {
    "sage": ["/path/to/sage/docs"]
  }
}
```

Use `brand-profile.json` → `creative_context` for portable brand-owned paths
when the profile itself should carry them:

```json
{
  "creative_context": {
    "knowledge_base_paths": [],
    "source_vault_paths": []
  }
}
```

Prefer `brand_vault_paths` / `brand_knowledge_base_paths` over global
`vault_paths` in multi-brand workspaces. Global paths are a compatibility
fallback for checkouts dedicated to one brand.

## Agent behavior

1. Call `brand_context_snapshot` before planning.
2. If `source_knowledge.configured` is true, call `brand_source_knowledge`
   with a focused query before planning.
3. Extract concrete product truth, approved vocabulary, proof moments, and
   negative constraints.
4. Convert durable findings into typed mutations or accepted prompt fields;
   do not paste private vault content into shared docs.
5. Keep brand scope strict: Sage vault facts should influence Sage only.

For Sage, source knowledge should improve specificity around governed skill
networks, prompt/knowledge curation, RLM feedback loops, libraries, DAOs,
trust, and distribution for agent capability.

## Sage planning-stage generation contract

Sage capability/explanatory plans now build a compact `sage_vault_brief` /
`sage_generation_contract` during planning, not only as optional agent
scratchpad context. The contract carries:

- one approved source-truth phrase,
- one concrete adoption/use scene,
- one style anchor,
- one logo rule,
- and a short hard-ban list.

The execution prompt treats this as a high-priority hard block so prompt
compression drops lower-signal prose before it drops the Sage source truth.
Branding for these assets should come from palette, routed/lattice/path motifs,
source/library/manifest objects, agent adoption/use scenes, and deterministic
typography/approved phrases; the Sage logo is provenance, not the story.

## Generated brand runtime prompts

`bgen create-brand` and `bgen start-testing` generate
`<brand-dir>/prompts/pi-full-pipeline.md`. The generated prompt is scoped to the
brand profile and approved copy, and instructs Pi to query `brand_source_knowledge`
only for that active brand. This keeps Sage-specific prompts from becoming the
default for unrelated brands.

Generated prompt files are safe to regenerate when they still contain the
`generated by brand-gen prompt pack` marker. If a user edits the prompt and
removes the marker, brand-gen preserves it unless regeneration is forced in code.
